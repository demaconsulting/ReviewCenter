### HelpPage

![Web Structure](WebView.svg)

#### Purpose

`HelpPage` is the built-in help of the web user interface. Its responsibilities are to list the help topics at
`/help`, to serve one page for each topic at `/help/{topic}`, to give those pages a common frame with links to the
neighboring topics, and to answer an unknown address under `/help/` with a friendly page. The help is static text and
screenshots rendered on the server as plain markup, with no live connection, and it is open to anonymous visitors. The
link to the help in the header of every page belongs to `App`. The unit consists of these Razor components and one
source file:

- `HelpPage` (`HelpPage.razor`): the index.
- `HelpTopicFrame` (`HelpTopicFrame.razor`): the common frame of a topic page.
- The topic pages `HelpGettingStartedPage`, `HelpCreatingReviewPage`, `HelpReadingReviewPage`, `HelpCommentsPage`,
  `HelpChecklistPage`, `HelpSigningPage`, `HelpAuditPage`, `HelpPlanningPage`, `HelpAttestationPage`,
  `HelpMembersPage`, `HelpApiTokensPage`, `HelpTwoFactorPage`, `HelpEvidenceSettingsPage`, and
  `HelpChecklistTemplatePage`: the text of one topic
  each.
- `HelpNotFoundPage` (`HelpNotFoundPage.razor`): the catch-all for an unknown address.
- `HelpTopics` (`HelpTopics.cs`): the list of topics.

#### Data Model

**HelpTopic**: a record of one topic with three values, **Slug** (the last part of the address, for example
`checklist`), **Title** (the text of the index link and the heading of the topic page), and **Summary** (one line that
says what the topic explains), and a derived **Href**, the address `/help/{Slug}`. The slugs are unique.

**HelpTopics.All**: the read-only list of topics in reading order. It feeds the index and the neighbor links of the
topic pages. Adding a topic is one page component with its route `/help/{slug}` and one entry in this list; the
index, the navigation links, and the tests then include it without further change. A topic that has a page but no
entry would be missing from the index, and an entry without a page would lead to the not-found page; the test of the
topic pages compares the routes of the pages with the list, so either mistake is caught.

**HelpTopicFrame component**: It has two parameters, **Slug**, the topic the page is about, and **ChildContent**, the
text of the topic. It finds the topic in the list, and renders a `main` element with the title of the topic as
heading, the content, and a navigation area at the bottom with outline-style links: Previous (the title of the
previous topic), All help topics, and Next (the title of the next topic). The first topic has no Previous link and the
last has no Next link.
The browser title is the title of the topic followed by "Help - ReviewCenter".

**Topic pages**: Each is a component that routes `/help/{slug}` and places its text inside a `HelpTopicFrame` with its
slug. The text is in cards (`card`), with figures for the screenshots. The screenshots are image files under
`wwwroot/help/`, requested with a path that begins `/help/`, loaded lazily, and each has alternative text that describes
what the picture shows and a caption.

**Signed attestation topic** (`HelpAttestationPage`, slug `signed-attestation`): The topic after Reviewers and signing
that explains the signed PDF of a complete review. It says when the download is offered and what the PDF lists; what the
signature proves (the content has not changed since the signing, and it was produced by the holder of the server key
named in the document) and what it does not (who the reviewers are, which is shown by the sign-offs in the record, and a
trusted signing time, because the time is the clock of the server and there is no time stamp authority); that the
default key is self-signed, not an organization key, and for development and test only; how an administrator points the
server at a certificate of a certificate store (`Attestation:Provider` and the thumbprint) or of a file
(`Attestation:Provider` set to `File`, `Attestation:CertificatePath`, the optional key file and password settings), a
document-signing certificate, a key of a store that is never exported and a key of a file that is held in memory only;
the warning for a certificate that ends within `Attestation:ExpiryWarningDays` or has ended; and what
`Attestation:RequireTrustedKey` does: it stops the server from
starting
for a self-signed key or a certificate without a signing key usage, and makes the review page show why attestation is
unavailable when a certificate stops being valid (for example expires) while the server runs. The topic also says that
the review page names a self-signed certificate that the administrator supplied (from a store or a file) as supplied by
the administrator, not as generated by the
server. It has one screenshot,
`signed-attestation-1.png`, of the review page with the download button and the key note. The topic also says that a
project admin can leave out the discussion threads, the names, the checklist wording, the file list, and the git
context, that every PDF then has a Content scope section that says what was omitted, and links to the Evidence settings
topic.

**Project members topic** (`HelpMembersPage`, slug `project-members`, title "Managing project members"): The topic after
Planning reviews and before the API tokens. It explains, in static text, that ordinary users see only the projects they
belong to while system administrators see all projects, and that a project admin or a system administrator manages the
members from the Members section of the project page; how to add
someone who has an account (the "+ Add member" button, the exact user name, no list of users, one message for every
reason a name cannot be added, and that repeated failures are audited and slow the person down); how to create an
account for someone new (the "Create a new account" button, the temporary password shown once, and that the person must
choose a new password at the first sign-in); how to change a role or remove a member and that a project always keeps at
least one project admin (a system administrator is exempt); what the review page shows for a reviewer who was removed
("No longer a project member", who cannot sign until added again); the project audit trail button, which also lists
every change of the evidence settings; and the Evidence settings button, which only a project admin or a system
administrator sees, with a link to its topic. It has no
screenshot. The audit trail topic (`HelpAuditPage`) also mentions that an administrator of a project can read the
entries of that project from the Audit trail button of the project page.

**API tokens topic** (`HelpApiTokensPage`, slug `api-tokens`, title "Automation and API tokens"): The topic after
Managing project members and before Evidence settings. It explains, in static text, what a personal access token is and
that it can never
sign; how to create
one on the Account page (the name, the expiry of 30, 90, or 365 days, that the value starting with `rcpat_` is shown
once,
the list of tokens, and the limit of 20 active tokens); how to revoke one; how to use one (a `curl` example that sends
it
as a bearer token, the list of endpoints including the evidence index and the OpenAPI document, and the use with
ReviewMark:
the token as the password of HTTP Basic credentials in an `evidence-source` of the `.reviewmark.yaml` file); that a
review created through the API is a
draft flagged as created via the API and still needs people to assign the reviewers and sign in the browser; and what
goes wrong (the same generic 401 for every refused token, including one whose owner still has to change a temporary
password, 429 for too many refused attempts, and that a token is for the
API only). It has one screenshot, `api-tokens-1.png`, of the token card of the Account page. The Account page links to
it
(see the `AccountPage` design). The topic also says that a request without any token may read the evidence index or an
attestation PDF of a project whose administrators opened that to anonymous readers, that a wrong token is still
refused, and links to the Evidence settings topic. The topic says that a signature needs a person who confirms it is
them again, with the password (and the code of the second factor, when there is one) or by signing in again at the
identity provider.

**Review integrity text**: Three topics explain the approval lock and the review rules, in static text. Reviewers and
signing (`HelpSigningPage`) has two list items: an approved review is locked (nobody can add comments, change answers,
change the files, or change the reviewers), a project admin or a system administrator can reopen it with a reason, the
reopen is recorded in the audit trail, the old signatures are kept as history, and the reviewers must sign again; and,
when the project requires independent reviewers (the default), the person who created a review cannot be one of its
reviewers and cannot sign it, where only the person who created the review in ReviewCenter is checked and the authors
of the commits are not. Reading a review (`HelpReadingReviewPage`) says that on an approved review the + buttons and the
comment forms are disabled while every file and diff can still be read, and links to Reviewers and signing. Managing
project members (`HelpMembersPage`) has a "Review rules" section that says the Review rules card of the project page is
also only for a project admin or a system administrator, switches on or off whether the person who created a review may
also be one of its reviewers, is on by default, and that every change is recorded in the audit trail.

**Identity provider text**: Three topics mention sign-in with an OpenID Connect provider, in static text that does not
depend on whether an administrator has turned it on (the pages have no access to the settings): Getting started
(`HelpGettingStartedPage`) says that the sign-in page may offer a "Sign in with ..." button, that the account is
created at the first sign-in without any project, and that a project admin has to add the person; Reviewers and signing
(`HelpSigningPage`) says that a person who signs in with a provider has no password here, presses "Confirm identity" on
the slot, signs in again at the provider, and returns to press "Sign", and that the confirmation is good for one
signature and a few minutes; and the API tokens topic, above. The summary of the Reviewers and signing topic in
`HelpTopics` reads "Reviewer slots, signing with your password or identity provider, and approval."

**Two-factor topic** (`HelpTwoFactorPage`, slug `two-factor`, title "Two-factor sign-in"): The topic after Automation and
API tokens and before Evidence settings. It explains, in static text, what the second factor is (a code from an
authenticator app added to the password, optional, for accounts with a ReviewCenter password only); how to turn it on
from the Two-factor authentication card of the Account page (the password, the secret shown once and the `otpauth://`
address, the first code, and the ten recovery codes shown once); how to sign in (a second page asks for the code, a code
works once, the step must be finished within 5 minutes); what to do after losing the phone (a recovery code instead of
the code, each works once, new recovery codes, and the reset by a system administrator from the Users page); that
signing a review needs the password and a current code, that recovery codes cannot sign, and that a code that was just
used to sign in must be followed by the next code; how to turn it off or renew the recovery codes; that changing the own
password needs a current code too; that an administrator who only sets a new password leaves the factor on; and that
wrong codes
count like wrong passwords for the lockout, that sessions already open stay valid after a turn-off or a reset, that API
tokens are not affected, that the setting `Identity:Totp:Enabled` can switch the feature off (then accounts that had it
are protected by the password alone), and that the changes are audited, never the codes. It has one screenshot,
`two-factor-1.png`, of the card with the factor on. The Account page links to it (see the `AccountPage` design), and
the Reviewers and signing topic (`HelpSigningPage`) mentions the code.

**Evidence settings topic** (`HelpEvidenceSettingsPage`, slug `evidence-settings`, title "Evidence settings"): The
topic after Two-factor sign-in. It explains, in static text, that only a project admin or a system
administrator can see and change the evidence settings, from the "Evidence settings" button of the project page, and
that every change is recorded in the audit trail of the project with the old and new values; the two anonymous
switches (Anonymous evidence index and Anonymous attestation PDFs), that both are off by default and independent, what
each opens, that the index alone is of no use to ReviewMark without the PDFs or credentials, that only those two
addresses can ever be anonymous, that anonymous requests are limited per address, that a project that has not opened a
switch answers as if it did not exist, and "Think before you turn them on" (anyone who can reach the server can read
what was opened, including threads and names that the PDFs still carry); the five content switches (Review discussion
threads, Reviewer names, Checklist wording, File list and hashes, Git context), that they are on by default and apply
to every PDF, what the PDF shows instead when each is off, what is always included, and that names typed into free text
are not removed; the regulatory warning (confirm with the quality or compliance lead before reducing a PDF); the
Content scope section that every PDF has; and the saving rule (one Save settings button, nothing is overwritten when
someone else changed the settings, a change applies to new downloads only). It has two screenshots,
`evidence-settings-1.png` (the page with the defaults) and `evidence-settings-2.png` (the page with content left out,
showing the warnings and the summary). The Signed attestation, Automation and API tokens, and Managing project members
topics link to it.

**Checklist template topic** (`HelpChecklistTemplatePage`, slug `checklist-template`, title "Checklist template"): The
last topic, after Evidence settings. It explains, in static text, that a project admin or a system administrator can
change the checklist that new reviews of the project start with, from the Checklist button of the project page, that
a project uses the built-in default until it is replaced, and that only the reviews created afterwards use the new
checklist while existing reviews keep exactly the checklist they were created with. It describes the steps (Export
current checklist, paste or choose a file of up to 256 KiB, Validate with all errors and their paths, the preview and
the differences, Replace checklist with its confirmation, and Reset to built-in default), the rule that a changed
definition needs another version label, that every change is recorded as `project.checklist-changed`, and the sample
that follows the lifecycle activities of IEC 62304, with the note that a template does not make a record compliant. It
has no screenshot.

**HelpNotFoundPage component**: It routes `/help/{*Slug}`, a catch-all with a parameter. The router prefers the fixed
routes of the topic pages, so only an address that is not a topic reaches it. It shows a message that there is no help
topic at the address, and a link to the index.

The links of the help are always whole addresses, never `#section` anchors: the document has a base address (see `App`),
so a link that begins `#` would lead to the home page and not to a place in the page.

Every interactive element and key value has a stable `data-testid` (see the test identifier rule of the Web
subsystem): `help-page` (index root), `help-topics` (the list), `help-topic-{slug}` (a card), `help-topic-link-{slug}`
(its link), `help-about-link`, `help-topic-page` (root of a topic page), `help-previous-link`, `help-index-link`,
`help-next-link`, and `help-not-found`. There is no `data-interactive` marker, because the pages have no live
connection.

#### Key Methods

**HelpTopics.Find**: Finds a topic by its slug.

- *Parameters*: `string slug`.
- *Returns*: The topic, or `null` when there is none with that slug.
- *Preconditions*: None.
- *Postconditions*: The slug is compared exactly, with ordinal comparison.

**HelpTopics.Previous** and **HelpTopics.Next**: Find the neighbors of a topic in reading order.

- *Parameters*: `string slug`.
- *Returns*: The topic before, or after, the given one; `null` for the first topic (Previous), the last topic (Next), or
  an unknown slug.
- *Preconditions*: None.
- *Postconditions*: The result is never the topic itself.

**Render (HelpPage)**: Produces the index: the heading "Help", a line of introduction, one card for each topic in the
list (a heading that is the link to the page of the topic, and the summary), and a line with a link to the About page.

**Render (HelpTopicFrame)**: Produces the frame described above for the topic named by `Slug`; for a slug that is not in
the list, the heading is "Help" and there are no neighbor links, only the index link.

**Render (HelpNotFoundPage)**: Produces the not-found message with the link to the index.

#### Error Handling

An address under `/help/` that is not a topic is not an error: `HelpNotFoundPage` shows the friendly message. A topic
page always passes a slug that is in the list, which the tests check. Otherwise the unit contains no error-producing
logic.

#### Dependencies

- **About page** (`AboutPage`) — the index links to it.
- **ASP.NET Core Blazor components** — page routing, page title support, and the base component types.

#### Callers

- **App** — the router in the `App` unit renders the pages of the help for their routes, and the header of `MainLayout`
  has a link to `/help` on every page.
